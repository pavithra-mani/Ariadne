# Ariadne: how to run it, the example data, and how to demo it

## 1. Run it

### Prerequisites
* Docker Desktop, running (`docker info` prints a server version).
* Free ports: **5173** (web), **8000** (API), **5433** (Postgres).
* Internet on the *first* start only: ChromaDB downloads a small embedding model (about 80 MB), cached afterwards in a Docker volume. If it cannot download, an offline fallback is used.

### Start
```bash
cd ariadne
docker compose up -d --build
```
The backend container seeds the database, ingests the knowledge base, then starts the API (40 to 90 s on first run).

| What | URL |
|---|---|
| App | http://localhost:5173 |
| API docs | http://localhost:8000/docs |
| Health | http://localhost:5173/api/health |

### Log in
Password for every demo account: **`ariadne123`**. One login per business:

| Login | Who |
|---|---|
| `mf1` … `mf10` | Mulberry farmers |
| `sf1` … `sf10` | Silkworm farmers |
| `reeler1` … `reeler5` | Reelers (each owns a warehouse) |
| `spinner1` … `spinner4` | Spinners / throwsters (each owns a warehouse) |

There is **no separate warehouse login**. A reeler keeps finished yarn in *its own* warehouse and a spinner keeps finished thread in *its own*. The warehouse appears as a card on that owner's dashboard, and rerouting pick-ups start from it.

### Stop, restart, reset
```bash
docker compose logs -f backend      # watch the backend
docker compose restart backend      # reload after adding models / keys / KB
docker compose down                 # stop (data kept)
docker compose down -v              # stop AND delete all data
```
**Reset between demo runs** (restores the seeded network and wipes incidents, deals, ledger, alerts, incident memory): UI **System → Reset demo data**, or `curl -X POST localhost:5173/api/system/reset-demo -H "Authorization: Bearer <token>"`.

### Local development (optional, hot reload)
```bash
docker compose up -d postgres && docker compose stop backend frontend
cd backend && python3.10 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m app.db.seed && .venv/bin/python -m app.rag.ingest
.venv/bin/uvicorn app.main:app --reload
cd ../frontend && npm install && npm run dev
```
Tests: `cd backend && .venv/bin/python -m pytest -q` (52 tests). Existing databases get new columns automatically on start, but a changed seed network needs *Reset demo data*.

### Troubleshooting
| Symptom | Fix |
|---|---|
| `Cannot connect to the Docker daemon` | Start Docker Desktop. If containers vanished after a Docker restart, `docker compose up -d`. |
| Port in use | Stop what uses 5173/8000/5433 or edit `ports:` in `docker-compose.yml`. |
| Login fails right after start | Backend still starting; wait for `Application startup complete` in `docker compose logs backend`. |
| Knowledge answers always refuse | `docker compose exec backend python -m app.rag.ingest --reset` |
| Incident status `error` | `docker compose logs backend` shows the exception. |

## 2. The example data

Real participant data does not exist publicly, so the demo uses a **synthetic but geographically real network** around Ramanagara, generated by `backend/app/db/seed.py` with a fixed random seed. **Every fresh start gives identical data**, so a rehearsed demo is repeatable.

* **10** mulberry farms, **10** silkworm farms, **5** reelers, **4** spinners, plus **9 warehouses** (one per reeler and spinner). Real towns: Ramanagara, Channapatna, Kanakapura, Magadi, Bidadi, Harohalli. Distances are haversine × 1.35.
* **Supply links** (what drives "who gets alerted"): each silkworm farm buys leaves from its 2 nearest mulberry farms and sells cocoons to its 2 nearest reelers; each reeler has several farmers and supplies its nearest spinners; each spinner buys from several reelers.
* **Products**: leaves → cocoon → yarn → thread. Prices: leaves ₹4/kg, cocoon ₹480/kg, yarn ₹4,800/kg, thread ₹5,600/kg. Shelf life: leaves 3 d, cocoon 8 d, yarn/thread 365 d.
* Each entity has stock, daily demand, lead time, age, money balance and capacity. These drive safety stock, reorder point, "sellable", "days until degradation" and utilisation.

### What the demo accounts see
| Login | Entity | Network |
|---|---|---|
| `mf1` | MF-01 (Kanakapura) | Own farm only. Leaves 2,498 kg, **degrading** (3-day shelf life). |
| `sf1` | SF-01 (Magadi) | Suppliers MF-06, MF-09 · buyers Reeling Unit R1, R3. Cocoon 134 kg, **reorder**. |
| `reeler1` | Reeling Unit R1 (Ramanagara) | 7 farmers (SF-01, 02, 05, 06, 07, 09, 10) · 4 spinners T1–T4 · own R1 Warehouse. Yarn 144 kg, cocoon 1,373 kg. |
| `spinner1` | Twisting Mill T1 (Ramanagara) | Reelers R1, R3, R4, R5 · own T1 Warehouse. Thread 182 kg, yarn input 177 kg. |

Visibility rules (enforced in the API, tested): a mulberry farmer sees only his farm; a silkworm farmer sees his mulberry suppliers and his reelers; a reeler sees his spinners and his farmers; a spinner sees his reelers. **Anything outside a user's visibility is anonymised** in incidents and deals ("Partner not visible to you"), keeping the numbers but not the identity.

### Sample photos (`data/images/`)
Flat-colour placeholders; the **stub classifier decides from the file name**.

| File | Use as | Stub result |
|---|---|---|
| `powdery_mildew_sample.jpg`, `leaf_blight_sample.jpg` | `mf*` | that disease (90 %) |
| `healthy_leaf.jpg` | `mf*` | healthy → no incident |
| `grasserie_sample.jpg` | `sf*` | grasserie |
| `blurry_photo.jpg`, `unknown_leaf.jpg` | `mf*` / `sf*` | 31 % → "diagnosis uncertain, ask an expert" |

Any real photo works if its file name contains a label (`flacherie_tray3.jpg`, `leaf_rust_plot2.jpg`). Labels: mulberry `healthy, leaf_rust, leaf_spot, powdery_mildew, leaf_blight, mosaic_virus`; silkworm `healthy, grasserie, flacherie, muscardine, pebrine`. The crop follows the login (`mf*` → mulberry, `sf*` → silkworm). "Affected ≈ %" in the Assistant changes severity and urgency.

### Knowledge base (`data/kb/`)
Eight short Markdown files (33 passages) that I wrote so the demo runs. **Placeholder text, not official CSB/FAO guidance.**

## 3. How your real material plugs in
Nothing in the agent graph changes.

### 3.1 Disease models
1. Put `mulberry.onnx` and `silkworm.onnx` in `data/models/`.
2. Beside each, a JSON file: `{"labels": ["healthy","leaf_rust",…], "input_size": 224, "mean": [0.485,0.456,0.406], "std": [0.229,0.224,0.225], "layout": "NCHW"}`.
3. `docker compose restart backend`. **System** tab shows *trained model* instead of *stub*.

Labels are normalised (`"Powdery Mildew"` → `powdery_mildew`) and should match `DISEASE_PROFILES` in `backend/app/graph/profiles.py`. Unknown labels and anything under 50 % confidence go to an expert instead of triggering action; add a profile so a new label is rated properly. For PyTorch / Paddle / Keras models a small loader is needed (`backend/app/vision/classifier.py`).

### 3.2 Knowledge base
Drop `.md`/`.txt`/`.pdf` into `data/kb/<topic>/` (optional front-matter `title:` / `source:`), then `docker compose exec backend python -m app.rag.ingest --reset` (replaces the corpus; delete the placeholders first). The eval set `data/eval/qa_set.json` names the placeholder files, so update it for your corpus.

### 3.3 Groq / LangSmith keys
`.env` in the repo root (see `.env.example`): `GROQ_API_KEY=…`, `LANGSMITH_API_KEY=…`, then `docker compose up -d backend`. Groq only turns verified facts into schema-checked text; numbers and decisions are locked. **System** tab shows live vs fallback.

### 3.4 Your own participants, stock, prices
Plain tables, loadable by SQL or script: `entities` (kind, name, village, lat/lon, balance, capacity, `warehouse_id`; warehouses have `owner_id`), `links` (supplier → buyer), `inventory` (on_hand, daily_demand, demand_std, lead_time_days, shelf_life_days, stocked_on, unit_price, is_finished), `users` (username, role = entity kind, entity_id). **There is no CSV importer yet**; send me your file layout and I will add one.

## 4. Demo script (about 15 minutes)

Run **Reset demo data** first. Use two browser profiles (or sign out/in) for steps that cross roles. The red badges in the left menu show unread **Alerts** and pending **Approvals** and refresh every few seconds.

**1. Roles and visibility** (Dashboard). `mf1` sees only itself; `sf1` adds MF-06/MF-09 and reelers R1/R3; `reeler1` sees spinners and 7 farmers plus its **warehouse card**; `spinner1` sees its reelers.

**2. Calculations and the stock trigger** (`reeler1` → Dashboard). Level bars show on-hand vs safety (red zone) and reorder point (tick).
* **Cocoon card → Update stock → set to 50 kg → Save.** The card turns *Below safety stock* and **Ariadne opens an incident by itself**: a banner says *"review 7 proposed deals in Approvals"*. It searched silkworm farms (within a growing radius, max 5 searches), routed pick-ups with OR-Tools to your own warehouse, and priced the purchase. Nothing has changed yet.
* **Approvals** → approve each proposal (the reeler approves his own purchase). Cocoon stock rises to about 1,100 kg (*Healthy*), the balance drops by the purchase and transport cost, and the selling farmers get a *"Pick-up scheduled"* alert.
* Any product that is not healthy also has an **"Ask Ariadne to restock this"** button (or *"protect my buyers"* for finished goods), which opens the same incident for products that were already low (for example `reeler3`'s thread, or `sf1`'s cocoon). Typing *"my cocoon stock is critical"* in the Assistant does the same.
* For a **finished** product (e.g. set yarn to 5 kg) the buyers who depend on you are alerted and their shortfall is re-sourced; for a **raw input** (cocoon, leaves, yarn for a spinner) Ariadne buys replacement stock upstream. Only one incident stays open per product, so repeated clicks do not create duplicates.

**3. Knowledge** (Knowledge tab). "Silkworms have milky fluid and climb the tray edge" → cited answer. "What is the capital of France?" → refuses.

**4. The main story: a supplier problem protects every buyer, automatically**
Whenever a supplier reports a disease, changes its stock, or runs low, Ariadne assesses each buyer. Any buyer that would fall below its **reorder point** gets **its own incident** that (1) alerts it, (2) calculates alternatives within at most 5 searches and routes them with OR-Tools, (3) proposes deals, and (4) waits for the buyer to approve or reject. The supplier does nothing extra.
* **Trigger it two ways as `mf3`** (try one, then reset): *Assistant* → upload `leaf_blight_sample.jpg`, affected **100 %**, **or** *Dashboard* → Leaves → *Update stock* → set to **100 kg**. The supplier's own incident just says "buyers alerted". The page banner says Ariadne opened incidents for **3 buyers**: `sf5`, `sf7`, `sf10`.
* Sign in as **`sf5`**. The **Alerts** and **Approvals** badges are lit, and the Dashboard shows two red alerts: *"Upstream alert: MF-03 … running low on leaves … shortfall 919 kg"* and *"Ariadne found 1 alternative source(s) for 1,060 kg of leaves (MF-04) … Route: 3 truck(s), 91 km, about 0h 56m from SF-05 … 1 deal proposal(s) await your approval"*.
* The **Supply outlook** card on `sf5`'s dashboard shows each supplier ("MF-03 can ship 0 of 184 kg · short 184 kg") and the expected shortfall. It reacts the moment a supplier edits stock or reports a disease. A buyer that still has enough stock shows *"covered by your stock"*.
* **Incidents** → the new incident is tagged *auto*, with the banner *"Opened automatically. Upstream: MF-03 … reported a 2,133 kg drop"*, its priority, the plan (searches, candidates, km) and the link to the cause.
* **Approvals** → the proposal with price, transport and route. **Approve** → stock, balance, ledger update; the seller is alerted. **Deals & ledger → Completed**.
* `mf3` sees none of this by name (mulberry farmers only see their own farm); their incident just shows "3 buyers… outside your visibility".
* Closing the loop: on `mf3`'s incident press **Mark as recovered**. The disease stops reducing downstream outlooks.
* A milder case: `mf1` + `powdery_mildew_sample.jpg` at 8 %: `sf3` gets a heads-up but its stock covers it, so no incident is opened.

**5. Silkworm → reelers.** `sf1` + `grasserie_sample.jpg` at 90 %: **P1** critical, mitigation steps, "your reelers were alerted". `reeler1` and `reeler3` get an *Upstream alert*; their cocoon stock absorbs the loss, so **no** buyer incident is opened, and the alert says so. Make it bite by first setting `reeler1`'s cocoon stock low, or use a bigger supplier event.

**6. Reeler outage → spinners.** `reeler1` → Assistant → *Low yarn output*, **100 %, 21 days**: **P1**. Ariadne opens incidents for all four spinners: `spinner1` (3 deals, ≈258 kg) and `spinner2` (2 deals, ≈109 kg) get proposals to approve; `spinner3` and `spinner4` are *escalated*: no alternative reeler had stock, so they get a *"Manual action needed"* alert. `reeler1` separately gets proposals to sell about 1,300 kg of stranded cocoons to other reelers.

**7. A reeler's own raw stock** (`reeler1` → Cocoon → *Update stock* → 50 kg). Ariadne opens an incident by itself, finds silkworm farms, routes pick-ups to the reeler's own warehouse, and proposes 7 purchases (`reeler1` approves). Pressing *Ask Ariadne to restock this* does the same for a product that is already low. For a **finished** product (yarn → 5 kg) it protects the buyers instead: spinners that would fall short each get their own incident.

**8. Spinner demand surge.** `spinner1` → target **800 kg in 7 days**: gap about 100 kg, **P2**, one deal approved by `spinner1`; reelers R1, R3, R4, R5 receive an *Incoming request* alert. Reset, then **1000 kg**: gap about 300 kg, **P1**, only about 107 kg can be sourced → *partial* plan and *Needs human follow-up*. Searches never exceed 5.

**9. System and Evaluation tabs.** What is live vs stub; the Table 5 baseline. Regenerate with `docker compose exec backend python -m app.eval.run --reset` (**wipes demo data**).

### Things that can surprise you live
* Pending proposals **reserve** the seller's stock, so a second unrelated report straight after may find fewer candidates. Reset between scenarios.
* The **approver is the buyer whose stock is being restored**. Because every buyer has its own incident, deals always appear in that buyer's own Approvals.
* A buyer's incident resumes only when **every** proposal of that incident is decided. If a buyer cannot be fully restocked, the residual loss is passed on to *its* buyers.
* Buyers already at or below their reorder point (for example `spinner4`'s yarn) always show *below reorder point* in their outlook; supplier events then push them further.
* Without a Groq key, wording is templated and plain.
* Sample images are flat colour blocks. A real model will behave differently.
* Quoted figures (≈1,137 kg, ≈223 kg, ≈100 kg …) come from the fixed seed on fresh data and shift if you change the seed code or ratios.
